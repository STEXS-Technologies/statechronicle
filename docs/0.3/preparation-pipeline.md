# Preparation ownership and ordered gates

Executor and the read-only Preparer share `Evaluation::execute_inner`.
Protected preparation and compatibility planning deliberately differ in ingress
policy and legacy marker handling. Preparation is not a committed result. This table
records current order, not a claim that F2 is complete.

| Stage | Authoritative owner and order |
| --- | --- |
| Protected ingress | Detached signature required; registry policy; reconstruct structural validation; bind principal; authorize. Legacy entry points retain their own documented ingress policy. |
| Envelope | Canonicalize intent; enforce size; check expiry with injected clock. |
| Legacy marker | Compatibility lanes read idempotency and may return empty events. Protected preparation skips the marker store entirely. |
| Authentication | Verify a present signature; check client authority-proof freshness. |
| Scope and state | Tenant scope/existence; state type; profile resolution; route; primary state lookup; profile-directed holder reload; projection type agreement. |
| Conflicts | Expected version, then profile access checks. |
| Custom identity | Registered operation and existing domain/schema pinning. |
| Authority | Required binding; evaluate configured authorities; aggregate policy; preserve unavailable > stale > denied precedence; check aggregate freshness. |
| Reduction | Shared profile evaluation, output state type and custom domain/schema. Native typed profiles decode once; default rules preserve check then apply. |
| Primary commitments | Private `PreparedEventStates`: checked version increment, existing or profile-defined unborn state, existing before hash or canonical unborn hash, canonical after hash. |
| Primary emission | Shared `emit_event` consumes checked commitments; event ID precedes injected timestamp. |
| Companion | Profile target, destination lookup, required source, profile companion reduction, the same checked commitment stage and emitter. |
| Legacy claim | One shared final write only for the legacy claiming lane, after all event construction. Protected preparation never claims. |
| Return | Allocate and return the complete ordered primary/companion event vector; no projection write or dispatch. |

`PreparedEventStates` owns the two complete commitments and has no public
constructor. The emitter cannot take an arbitrary unchecked pair. The extraction
removes the two implementations of version/unborn/hash/event construction and
the second legacy intent-write branch. It preserves profile-specific reduction,
addressing and authorization responsibilities rather than merging their contracts.

Failure ordering matters. Version overflow occurs before unborn-state creation
or event-ID consumption. If a companion fails, the primary event ID may already
have been consumed, as in the original implementation; no event vector or intent
claim escapes. An existing projection's before hash is retained, not silently
recomputed or reinterpreted. Clock/ID callbacks remain host-injected and must not
perform durable writes or dispatch.

`crates/statechronicle-executor/tests/emission_contract.rs` freezes canonical
creation and debit/credit event-vector digests generated by the unmodified
`v0.2.0` production implementation. The same test file executes against both
original and candidate. It also freezes primary/companion version-overflow
refusal, absence of legacy claims and subsequent event-ID consumption. These
planning fixtures use the original test-only permissive signature verifier and
in-memory adapters; they qualify event semantics, not authenticated ingress or
physical durability. Existing protected-ingress and ledger tests cover their
separate boundaries.

The shared preparation stages and native decode-once execution have since been
implemented. The broader multi-fault legacy matrix below extends the original
ingress and emission fixtures. Protected batch and coordinated settlement now
share that core; see [batch preparation](batch-preparation.md). The compatibility
fixtures below retain their original narrower scope and do not establish the
full protected durable or final release gates.


## Shared player ingress decisions

Signature presence, principal binding/authorization and key-lifecycle resolution
now each have one private decision implementation. Callers choose order explicitly;
a common helper must not silently standardize different compatibility policies.

| Lane | Order before the execution core |
| --- | --- |
| Trusted authenticated planning | Principal binding → explicit authorizer |
| Player planning/durable sink | Required signature → principal binding → authorizer |
| Single player registry lanes | Required signature → key registry → existing player lane |
| Player registry batch | Per item: required signature → principal binding → authorizer → registry; then execute the whole batch |
| Protected preparation | Required signature → registry → reconstruct structural validation → principal binding → authorizer |

Registry calls retain the independently supplied principal subject, intent tenant,
operation and intent creation time. Key policy does not replace cryptographic
verification. The helpers add no store writes, dispatch, new default policy,
public trait or dependency. Legacy wrappers retain their marker/sink behavior.

`tests/ingress_order.rs` freezes multi-fault precedence against the unmodified
original release: signature absence beats all other failures; registry failure
beats principal/policy failures in single registry lanes; batch principal
mismatch beats authorization and registry; batch policy denial beats registry.
The same test file passes original and candidate. Placeholder signatures are
intentional because all fixtures must refuse before cryptographic verification.
The final fixture only renames unrelated local variables for strict Clippy;
expected errors and callback traces are unchanged. Existing real-signature and
protected-preparation tests cover accepted ingress and key policy separately.

The event emitter's documentation and lint scope are attached to their intended
methods again; the prior extraction had left the execution-core comment and
allowance on the new emitter. This correction changes no runtime behavior.
Full F2 gate decomposition and the remaining release phases are still open.


## Execution-core multi-fault characterization

An external 23,544-row consumer now matches the actual original release and
`f5b922f` exactly on complete errors, canonical events, marker effects and ordered
callbacks. Six native/built-in templates exercise nine legacy entry points with
zero, single and pairwise faults. All 54 positive controls emit events. A temporary
archive mutation that preserves the clock but removes expiry refusal changes
1,410 expired-case outcomes and fails comparison. See [the complete manifests,
negative controls and limitations](evidence/f2/executor-order/README.md).

These are sentinel compatibility hosts and sinks. They do not qualify protected
canonical settlement, real transaction rollback or physical crash recovery.


## Checked profile context

The private `PreparedProfile` now owns the resolved profile/policy, state type
and observed projection with a borrowed immutable intent. Its only constructor
performs scope/state/version/access/custom-schema checks in their original order.
Authority, reduction and event construction use that context; event construction
consumes it. Existing `PreparedEventStates` remains the commitment owner. The
outer evaluation retains compatibility marker reads/claims, allocating the final
event vector only after any claim. No marker capability enters the profile stage.

This is a checked profile record, not an authentication seal or receipt. Signature
and principal policy remain explicit ingress decisions; clocks and event IDs
still come from the shared evaluation. The [retained `4c55fe6` evidence](
evidence/f2/prepared-profile-a52d53f/README.md) records original/control/candidate
parity, full finite tests, external consumers, source growth and bounded matched
performance/allocation observations. Broader F2 and release gates remain open.


## Compatibility coordinator completion

Ordinary batch, same-tenant settlement and the two cross-tenant coordinators
share private `BatchCompletion`. Its enum keeps a symbolic handle and a durable
sink mutually exclusive; lazy begin avoids even constructing a boxed transaction
future on sink routes. Success and refusal handling have one owner, while callers
keep result ownership, group flattening, validation policies and refusal context.
Tenant partitioning and settle selection also share private deterministic helpers.

The [retained evidence](evidence/f2/batch-completion/README.md) includes 10,128
original coordinator traces and a negative control detected solely by side
effects. This does not merge compatibility completion with canonical LedgerStore
atomicity or recovery. A refusing-sink p95 concern remains open alongside the
broader F2/F6/F8 requirements.
